# Deposit wallet collection

The service transfers supported assets to the treasury on the same chain. It does not exchange or bridge tokens. The deposit ledger, client balances and referral rewards remain separate.

Apply `treasury.sql` to the project's Supabase database. The migration adds a service-role-only journal, one worker lease per chain and a queue for new credited deposits. Each enabled chain also walks the current registered wallet addresses, including separate addresses on older EVM records. Historical addresses without a matching custody record require reconciliation. A restart resumes a signed transaction by hash. Inspect confirmed transfers in `treasury_transfers`; inspect `chain,hold_reason` in `treasury_lanes`. The pending column contains a signed transaction and belongs exclusively to the service role.

Set `TREASURY_MODE` to `observe` to preview eligible operations in the service log. Observing does not unlock customer wallet keys or broadcast. Set it to `live` only for the approved destinations and budget. Omitted or `off` leaves the new worker inactive. Set `TREASURY_POLICY` to a JSON object keyed by the enabled chains: `ethereum`, `bsc`, `opbnb`, `tron`. Each entry needs decimal strings `maxFee`, `dailyFee` and `minNative` denominated in that chain's native coin. `minStable` defaults to one token. The charge reserved for the daily budget includes the full amount of each gas advance as well as its sending fee. It is a conservative ceiling, not an invoice for consumed gas.

EVM collections use the project's `ADMIN_SWEEP_ADDRESS`. TRON needs its own `ADMIN_TRON_SWEEP_ADDRESS`, verified as a treasury account controlled by the project. Never infer a TRON destination from an exchange deposit address. `TREASURY_EVM_GAS_PRIVATE_KEY` and `TRON_GAS_PRIVATE_KEY` optionally configure a project-controlled gas sponsor. Set these only through the service's secret store. Use a dedicated EVM sponsor per project on a shared chain to prevent nonce collisions with other services. Existing gas on a deposit address can fund its own transfer. TRC20 wallets that have tokens but lack an activated TRON account need a sponsor. If the node cannot simulate from an inactive source, an optional positive integer `activationEnergy` bounds the activation advance. The service reserves creation costs and re-simulates the token transfer after activation.

The default token list is USDT and USDC on Ethereum and BSC, USDT on opBNB and USDT on TRON. Native ETH, BNB and TRX are collected after eligible tokens, minus a fee reserve. Reviewed ERC20 and TRC20 contracts can be added as `tokens` objects with `address`, `symbol`, numeric `decimals` and a decimal-string `minimum`. Recognize tokens by chain and contract. Metadata or units from an unsolicited token do not authorize a transfer. A reviewed TRC10 asset uses the same fields with `standard` set to `TRC10` and its numeric token ID as the address.

The existing BSC sweeper remains active by default. To replace it, first let in-flight BSC transfers settle, set `TREASURY_BSC_OWNER=worker` and configure the BSC policy. Keep that owner setting while pausing or reconciling the new worker. Confirm on-chain inclusion for a held transaction and its signer nonce or TRON expiration before resuming a lane. Do not discard a pending journal or fund the same source manually while it is being reconciled. A changed recipient with a pending transaction places the lane on hold.

Run `node --test treasury.test.cjs` for the offline transaction and recovery checks.
